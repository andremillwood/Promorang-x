# PROMORANG Economy System Design Lab v1

## Purpose

The five persistent participant destinations simplify navigation. They do not collapse PROMORANG's product economy.

Before production convergence, each major economy system receives its own Design Lab treatment: object language, lifecycle states, mobile/desktop behavior, trust, economics, empty/error considerations, and the way the system returns into Today / Discover / Card / Vault / You.

## Locked shell

- Today — what matters now
- Discover — what is forming, available, nearby or worth keeping
- Card — what can open now
- Vault — what remains, has value, or has history
- You — who the participant is through participation

These destinations remain stable while deeper systems retain dedicated detail flows.

## 12 — Discovery & Demand

### Product job
Make latent demand visible without pretending demand is confirmed supply.

### Core lifecycle
Signal → Results → Demand forming → Activated Moment

### Required states
- open for signals
- signal submitted
- directional results
- demand forming
- host/merchant/creator response
- activated Moment
- closed / expired
- insufficient signal

### Trust rules
- always distinguish demand from confirmed availability
- show population / denominator and time scope where meaningful
- do not imply that voting guarantees an event or offer
- when supply answers demand, show the issuer / host responsible

### Return surfaces
- Today — urgent poll or newly activated response
- Discover — primary home for polls and demand formation
- You — signal / participation history

## 13 — Pieces & Provenance

### Product job
Make verified participation capable of becoming a durable Kept object with provenance, identity and explicit utility.

### Core lifecycle
Earned → Kept → Listed → Transferred

### Required states
- earned from participation
- bought from marketplace
- kept
- utility active / expired
- listed
- sale pending
- transferred
- provenance history

### Trust rules
- origin distinguishes earned from purchased
- provenance outranks speculative market value
- utility must be concrete and time-bounded
- never imply guaranteed appreciation or investment return

### Return surfaces
- Discover — emerging / discoverable Pieces
- Vault — owned collection
- You — identity through kept objects
- Marketplace — exchange context

## 14 — Piece Marketplace

### Product job
Enable trusted exchange without turning PROMORANG into a crypto-terminal aesthetic.

### Core flow
Browse → Detail → Review purchase → Settlement → Ownership / provenance update

Seller flow:
Owned Piece → List → Review terms / fees → Active listing → Sale / cancel

### Required states
- browse / filter
- detail / provenance
- buy
- insufficient Gems
- sold / unavailable
- list mine
- edit / cancel listing
- transaction history

### Trust rules
- provenance before price
- seller / holder state visible
- fees and settlement explicit before confirmation
- utility separate from ask price
- irreversible actions require clear confirmation

### Return surfaces
- Discover — market entry and featured Pieces
- Vault — collection and list/sell entry
- You — collection identity, not trading P&L

## 15 — PromoKeys & Perks

### Product job
Create compact gated access that feels different from PromoCard and clearly communicates unlock / use conditions.

### Core lifecycle
Locked → Unlocked → Active → Expiring → Used → Proof

### Required states
- unlock requirement
- newly unlocked
- activation terms
- active
- expiring
- expired
- merchant validation
- used / proof returned

### Trust rules
- issuer, venue, validity and redemption requirements visible before use
- locked state explains how to unlock
- used state stops behaving like access and returns as Proof

### Return surfaces
- Today — expiring / newly unlocked Keys
- Card — primary home for active access
- Vault — proof after use

## 16 — PromoShare & Draws

### Product job
Make named draws legible, exciting and auditable.

### Core lifecycle
Open → Closing → Ticket set locked → Drawing → Result → Claim / history

### Required states
- prize named
- draw named
- ticket count
- ticket provenance
- countdown / close time
- drawing
- result
- winner / non-winner
- reward claim
- completed draw history

### Trust rules
- every ticket belongs to a named draw
- tickets are not Gems, Points, leaderboard weight, or cash
- show how tickets were earned
- lock ticket set at close
- preserve result and claim history

### Return surfaces
- Today — closing-soon draw
- Vault — primary ticket/draw history
- You — draw participation history

## 17 — Save & Win

### Product job
Let users park Gems, retain principal ownership, receive tickets to a named draw, and potentially receive additional Gems from a committed prize pool.

### Core lifecycle
Choose amount → Confirm → Parked → Tickets received → Draw → Principal returned / available → Result history

### Required states
- amount selection
- confirmation
- parked principal
- tickets earned
- draw pending
- draw result
- unpark / return where rules allow
- transaction history

### Trust rules
- parked principal must never look spent or lost
- prize pool is distinct from participant principal
- named draw and ticket allocation remain explicit
- source of prize funding / committed prize amount should be stated in production

### Return surfaces
- Vault — primary home
- Today — draw closing / result signal
- You — draw participation history

## 18 — Value System

### Gems
Spendable internal platform value.

UI needs:
- balance
- spending / receiving / parking actions
- transaction ledger
- source and destination
- marketplace and Save & Win context

### Points
Record of participation.

UI needs:
- earned reason
- progression / eligibility context where relevant
- history
- no cash-like visual treatment

### Tickets
Entries assigned to named draws.

UI needs:
- draw-specific balance
- ticket provenance
- close time / result
- historical draw association

## Cross-system principle

Utility icons may stay familiar. PROMORANG-specific meaning remains proprietary through Move / Explore / Return / Proof / Kept.

## Production convergence gate

Do not replace the current participant economy surfaces solely because the five-destination shell looks cleaner. A system should migrate only after:

1. its Design Lab lifecycle is approved,
2. trust and economic semantics are explicit,
3. mobile and desktop layouts are reviewed,
4. real-data empty/loading/error states are reconciled,
5. current production functionality has been mapped so no economy behavior is silently removed.
