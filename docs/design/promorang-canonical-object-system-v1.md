# PROMORANG Canonical Object System v1

## Thesis

PROMORANG should not have a Participant version of a Moment, a Host version of a Moment, a Brand version of a Moment, and an Admin version of a Moment that drift into different product meanings.

There is one canonical object. Stakeholders receive different controls, evidence emphasis, and next actions around the same underlying truth.

> **One object. Many lenses. One history.**

## Shared semantic lifecycle

PROMORANG's semantic marks describe transformation, not decoration:

- **Explore** — possibility, demand, forming state
- **Move** — issue, publish, launch, operate, transfer
- **Proof** — an evidence boundary is crossed
- **Return** — value, customer behavior, decision or correction comes back
- **Kept** — provenance, ownership, residue and history remain

Not every object uses every mark in the same order, but every lifecycle must make its boundaries explicit.

## Shape grammar

PROMORANG uses a rectangular layout grid for legibility, responsiveness and reliable interaction targets. The visible product objects do **not** all inherit that rectangle.

> **Rectangles define layout. Objects define personality.**

A canonical object should remain recognizable by silhouette, aspect ratio, layering and material treatment even if copy and color are removed.

### Silhouette families

- **Moment** — poster/pass hybrid with a cut edge and world-facing media.
- **Scene** — spatial field / constellation rather than a card.
- **Discovery** — open signal field with distributed nodes and threshold path.
- **Perk** — compact benefit token/chip.
- **Offer** — long ruled commercial instrument with inventory/rules geometry.
- **PromoKey** — carried entitlement fob/key with a handle/opening.
- **Pass / Ticket** — horizontal ticket with detachable/perforated stub.
- **Opportunity / Mission** — commission folder / layered brief.
- **Proof** — clipped evidence certificate/seal.
- **Receipt** — narrow paper roll with durable write residue.
- **Piece** — compact framed collectible/relic.
- **PromoShare** — serialized ticket family / fan.
- **Save & Win** — protected reserve/vault pod.
- **Value species** — Gems, Points and Tickets deliberately use different silhouettes.

### Semantic shape cues

The shared lifecycle may influence geometry without forcing one universal shape:

- **Move** — directional/open edge, notch, issue or launch cue.
- **Explore** — distributed path, orbit, dots or expanding field.
- **Proof** — seal, stamp, clipped edge, boundary crossing.
- **Return** — fold-back, receipt residue, loop/return cue.
- **Kept** — contained, framed, archival or collectible treatment.

### Layering rule

PROMORANG may use controlled overlap where the relationship is meaningful:

- ticket tucked behind a Moment;
- evidence attached to a dossier;
- receipt left by a validation;
- earlier draft visible beneath current draft;
- detached pass stub after use;
- proof seal crossing an evidence boundary;
- Piece emerging from retained history;
- amendment slip attached to an Admin case.

This is not decorative skeuomorphism. The layer must communicate state, provenance, dependency or consequence.

### Shape quality gate

For the signature form of a canonical object:

> **If copy and color are removed, can a reviewer still distinguish Moment, PromoKey, Pass, Receipt, Piece, Proof and Case/Evidence objects by silhouette and composition?**

If not, the object is still relying too heavily on generic container styling.

## Canonical objects

### 1. Moment
A bounded thing happening in the world that can be anticipated, accessed, attended, proved and remembered.

Canonical lifecycle:
`FORMING → OPEN → LIVE → CLOSED → KEPT`

### 2. Scene
A durable cultural or interest territory organizing people, Moments, demand, places and kept history.

Canonical lifecycle:
`SIGNAL → FORMING → ACTIVE → RETURNING → CULTURAL RECORD`

### 3. Discovery
A market signal that something may be worth forming, supplying, activating or moving toward.

Canonical lifecycle:
`SIGNAL → DEMAND → THRESHOLD → ACTIVATED → ARCHIVED`

### 4. Perk
The benefit itself: what a person receives.

Canonical lifecycle:
`DEFINED → AVAILABLE → UNLOCKED → USED → REMEMBERED`

### 5. Offer
The commercial configuration around a Perk: rules, inventory, validity, place, price/requirement and fulfillment conditions.

Canonical lifecycle:
`DRAFT → PUBLISHED → CLAIMED → VALIDATED → CLOSED`

**Claim ≠ validation ≠ purchase ≠ fulfillment.**

### 6. PromoKey
A specific entitlement object that unlocks or carries access to a Perk, Moment, gated opportunity or funded drop.

Canonical lifecycle:
`LOCKED → UNLOCKED → ACTIVE → USED → KEPT PROOF`

### 7. Pass / Ticket
A serialized right or reservation to cross an access boundary.

Canonical lifecycle:
`ISSUED → HELD → PRESENTED → CHECKED IN → ARCHIVED`

**RSVP intent ≠ attendance.**

### 8. Opportunity / Mission
A bounded ask for useful action with explicit outcome, deliverable, proof requirement and value terms.

Canonical lifecycle:
`OPEN → ACCEPTED → SUBMITTED → APPROVED → SETTLED / KEPT`

**Submitted ≠ approved ≠ settled.**

### 9. Proof
Evidence that an action crossed a defined verification boundary.

Canonical lifecycle:
`OBSERVED → ATTRIBUTED → VERIFIED → CONSEQUENCE → AUDITABLE`

Proof is contextual. Verification of one fact does not silently verify every downstream outcome.

### 10. Receipt
A durable human-readable record of a confirmed action, state change or consequence.

Canonical lifecycle:
`WRITE → IDENTIFY → CONSEQUENCE → RETAIN`

Receipt is a cross-role trust object.

### 11. Piece
A kept cultural/provenance object created by meaningful verified participation. Ownership can change; provenance does not.

Canonical lifecycle:
`EARNED → KEPT → LISTED → TRANSFERRED → PROVENANCE`

Pieces must not imply guaranteed appreciation, investment return or cash equivalence.

### 12. PromoShare
A named promotional draw with serialized tickets, committed prize terms, visible states and auditable fulfillment.

Canonical lifecycle:
`OPEN → CLOSING → DRAWING → RESULT → FULFILLED`

### 13. Save & Win
A protected-value mechanic where parked Gems remain participant principal while promotional prize eligibility is tracked separately.

Canonical lifecycle:
`CHOOSE → PARKED → DRAW → RETURNED → HISTORY`

Principal and promotional pool remain separate.

### 14. Gems / Points / Tickets
Distinct value species.

- **Gems** — spendable platform value.
- **Points** — participation/progression record.
- **Tickets** — serialized eligibility belonging to named draws.

They must not collapse into one ambiguous balance or one visual token.

## Role-lens rule

Every canonical object must answer, for each stakeholder:

1. **Job** — why this object exists to them.
2. **Action** — what they may legitimately do.
3. **Evidence** — what they may inspect or create.
4. **Consequence** — what changes when the boundary is crossed.

Roles:
- Participant
- Host
- Merchant / Venue
- Creator
- Brand
- Agency
- Admin

## Participant requirement

Participant Next remains a primary quality and personality reference. Shared objects must preserve the participant's tangible object language—tickets, receipts, keys, Pieces, access, world context, semantic marks—while receiving complementary operator views rather than unrelated dashboard representations.

## Operator requirement

Stakeholder Next remains the operational-maturity reference. Shared objects must preserve:
- explicit states
- failure/exception states
- source evidence
- durable residue
- truthful consequences
- job-specific controls

## Design rule

> **If changing stakeholder role changes the meaning or historical truth of the object, the design has failed.**

The stakeholder may see different controls and emphasis. The object identity, lifecycle truth, serial/provenance and confirmed history remain shared.

## Next convergence

After object identities are visually and semantically approved:

1. Map each canonical object to existing production tables/hooks/services/routes.
2. Identify where current UI is compatible, fragmented, misleading or absent.
3. Reuse shared object components across Participant Next and Stakeholder Next.
4. Add missing backend state only when the intended canonical lifecycle cannot be represented truthfully.
5. Migrate role-specific surfaces around the same object components and lifecycle definitions.
