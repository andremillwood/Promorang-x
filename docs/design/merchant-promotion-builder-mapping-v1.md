# Merchant Promotion Builder — Intent Mapping v1

This document defines how simple merchant intent maps to the existing offer engine.

## 1. Get more customers

Merchant inputs:
- offer value
- availability window
- quantity/capacity
- optional location

Default engine mapping:

```text
reward_type = coupon
fulfillment_type = merchant_validation
channel = direct
trigger_event = claim
funding_source = merchant_inventory
proof_required = qr_gps
availability = local
surface = place
per_user_limit = 1
status = active
```

If a date/time window is supplied, use local availability and preserve the schedule in offer metadata/terms.

## 2. Bring customers back

Merchant inputs:
- return value
- eligible audience / prior visit rule
- expiry
- capacity

Default engine mapping:

```text
reward_type = coupon
fulfillment_type = merchant_validation
channel = direct
trigger_event = claim
funding_source = merchant_inventory
proof_required = qr_gps
availability = local
surface = place
per_user_limit = 1
status = active
```

Eligibility should be derived from prior verified merchant/customer activity rather than asking the merchant to configure trigger semantics.

## 3. Promote something

Merchant inputs:
- product/service
- promotion type
- value
- quantity
- availability

Default engine mapping for in-store product:

```text
reward_type = coupon
fulfillment_type = merchant_validation
channel = direct
trigger_event = claim
funding_source = merchant_inventory
proof_required = purchase_code
availability = local
surface = commerce
per_user_limit = 1
status = active
```

For shippable/e-commerce items:

```text
fulfillment_type = shipping
availability = anywhere
surface = commerce
```

## 4. Fill a slow period

Merchant inputs:
- days
- start/end time
- customer value
- capacity

Default engine mapping:

```text
reward_type = coupon
fulfillment_type = merchant_validation
channel = moment
trigger_event = checkin
funding_source = merchant_inventory
proof_required = qr_gps
availability = local
surface = place
per_user_limit = 1
status = active
```

The merchant sees the schedule and offer. They do not configure `moment`, `checkin` or `qr_gps` directly.

## 5. Get more bookings

Merchant inputs:
- service
- available window
- booking incentive
- capacity

Suggested mapping:

```text
reward_type = coupon
fulfillment_type = automatic OR merchant_validation depending on booking infrastructure
channel = direct
trigger_event = claim
funding_source = merchant_inventory
proof_required = booking_confirmation
availability = local OR anywhere depending on service
surface = commerce
status = active
```

## 6. Increase spending

Merchant inputs:
- minimum spend threshold
- customer reward
- expiry
- capacity

Suggested mapping:

```text
reward_type = coupon
fulfillment_type = merchant_validation
channel = direct
trigger_event = claim
funding_source = merchant_inventory
proof_required = purchase_code
availability = local
surface = commerce
status = active
```

The spend threshold should be expressed as a qualification rule generated by the builder.

## 7. Get reviews or customer content

Merchant inputs:
- requested action
- destination/platform
- reward/value
- quantity

Default engine mapping:

```text
channel = content
trigger_event = share OR proof_verified
proof_required = post_url OR review_url
fulfillment_type = automatic OR manual
availability = anywhere
surface = commerce
```

If the reward has cash-equivalent liability, preserve existing funding and committed-value guards.

## 8. Reward existing customers

Merchant inputs:
- audience/eligibility
- reward
- quantity/expiry

Default mapping depends on reward type, but eligibility should come from customer history and merchant relationship data rather than exposing Promorang object mechanics.

## Advanced mode

Advanced mode may allow explicit configuration of:

- reward_type
- fulfillment_type
- channel
- trigger_event
- source_id
- funding_source
- proof_required
- committed_value
- promoshare_rate
- availability
- surface
- city_slug

Advanced mode must not be the default merchant experience.

## Safety invariants

The simplification layer must not bypass:

- committed-value checks
- maximum liability checks
- existing authorization / organization scoping
- merchant-only redemption controls
- per-user redemption limits
- existing offer status validation

The UI should hide complexity, not remove financial or authorization safeguards.
