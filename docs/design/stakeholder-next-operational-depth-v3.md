# Stakeholder Next V3 — Operational Depth

## Purpose

V3 moves the Stakeholder Next review environment from editorial presentation boards toward believable operating workspaces while preserving the five-destination role model established in V2.

Participant Next remains the quality benchmark for clarity, object identity and PROMORANG character. Stakeholder Next differs in one important way: professional roles require enough state, history, proof, actions and consequences to operate real work for sustained periods of time.

## Design rule

**Keep the world. Increase the work.**

Do not return to generic SaaS dashboards. Increase operational density by deepening the work objects themselves.

Every visible detail should help a user identify, authenticate, locate, quantify, time, authorize, record, review or transform work.

## Global changes

- Replace the repeated giant manifesto hero with a compact operating header containing:
  - stakeholder context;
  - current job;
  - current move;
  - workspace status.
- Preserve the five role destinations.
- Reduce unused desktop canvas by making primary objects carry more working state.
- Reserve expressive serif typography for object/document titles rather than every page headline.
- Keep `Illustrative review data` explicit.
- Keep `Compare current product` as a review-only control.

## Creator

### Production Room
Adds:
- brief identity and revision state;
- deliverable metadata;
- requirements checklist;
- version history;
- review thread;
- published-link state;
- proof dependency;
- submission gating.

The submission action is visibly unavailable until the missing proof requirement is satisfied.

### Proof Dossier
Separates:
- observed;
- attributed;
- verified;
- creator ledger value.

### Value Ledger
Keeps pending, approved and settled states distinct and explicitly preserves `approved != payout sent`.

## Host

### Door Board
Carries:
- RSVP intent;
- checked-in attendance;
- walk-ins;
- exceptions;
- scanner readiness;
- arrival-ledger state;
- unresolved pass mismatch.

### Proof Close
Each proof item receives an individual evidence state and explicit approve/reject action.

## Merchant / Venue

### Offer Instruments
Offers stop behaving like generic cards. Each instrument carries:
- offer ID;
- state;
- allocation;
- validated uses;
- remaining quantity;
- validity window;
- place;
- operating rules;
- pause/edit/open actions.

### Validation Device
Validation remains explicitly separate from purchase and fulfillment.

### Order Board
Payment, fulfillment and refund remain separate columns/states.

## Brand

### Activation Dossier
The dossier now accumulates:
- observed actions;
- attributed actions;
- verified actions;
- unresolved actions;
- evidence-source counts;
- decision deadline;
- activity trace.

### Evidence Pack
Evidence is represented as a ledger of sources, proof strength and timestamps rather than a static scorecard.

### Decision Record
Stop / Change / Scale must preserve the evidence-pack version, owner, timestamp, rationale and next operating change.

## Agency

- Client context stays explicit.
- Managed work shows preparation, approval, live and proof stages with ownership boundaries.
- Managed Result Pack retains client ownership.
- Expansion work cites proven evidence rather than projected ROI.

## Admin

- Priority queue is case-oriented rather than subsystem-oriented.
- Cases retain original record, dispute, evidence and pending decision.
- Economy makes queued / paid / held states explicit.
- Health emphasizes traceability and append-only correction logic.

## Relationship to live convergence

V3 is an illustrative review benchmark. It does not replace the live-converged Host, Merchant, Creator, Brand, Agency or Admin components.

Once V3 is visually and behaviorally approved, its object density and interaction patterns should selectively converge into those live components while preserving their existing real hooks, mutations and domain truth.

## Migration gate

A Stakeholder Next object is ready to influence production only when it has:

1. clear object identity;
2. truthful lifecycle state;
3. actionable operating detail;
4. history or residue where the work changes over time;
5. failure/blocked state;
6. evidence/proof boundary where relevant;
7. responsive behavior;
8. no fabricated production claim;
9. a mapped existing production capability or an explicitly documented product gap.
