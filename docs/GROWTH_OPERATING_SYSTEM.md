# Promorang Growth Operating System

Last updated: 2026-07-14

## Operating decision

Promorang's growth north star is:

> Weekly verified outcomes generated by active Moments.

The platform should optimize two loops before adding more incentive systems.

### Participant loop

`First touch → signup → onboarding → Moment join → verified outcome → share/referral → referred verified outcome → repeat outcome`

### Commercial loop

`Brand or host intent → funded activation → PromoPush distribution → Moment join → verified outcome → attributable revenue → repeat campaign`

PromoPush, PromoShare, referrals, Pioneer Points, Pieces, rewards, and lifecycle email support these loops. They are not separate north stars.

## Relationship to Pioneer Points

The systems answer different questions:

- Growth asks: **Did the network create more verified outcomes, repeat activity, and attributable revenue?**
- Pioneer asks: **Who made meaningful, verified contributions to building that network?**

Pioneer remains the durable seasonal contribution ledger. Its points must never be counted as revenue, purchased conversions, or a substitute for verified outcomes. The Growth scorecard includes a read-only Pioneer overlay showing verified receipts, verified points, unique contributors, pending reviews, open fraud flags, and contribution by role. This lets operators inspect whether growth is being created broadly and credibly without blending the two accounting systems.

Shared authoritative moments include:

- A qualified referral creates a growth amplification signal and a Pioneer referrer receipt.
- Verified participation creates a growth outcome and may create a Pioneer member receipt.
- A completed Moment contributes to growth outcomes and can create host and venue Pioneer receipts.
- Published attributable content can create a creator Pioneer receipt and later be evaluated by the outcomes it drives.

Pioneer season freezes, allocations, caps, verification, reversals, and funded-pool controls remain governed by `docs/PIONEER_POINTS.md`.

## Canonical events

| Event | Stage | Meaning | Authoritative source |
| --- | --- | --- | --- |
| `page_view` | acquired | A route was viewed | Web growth tracker |
| `cta_clicked` | captured | A measured acquisition CTA was selected | Web marketing intent |
| `signup_started` | captured | Signup was submitted | Auth page |
| `signup_completed` | captured | A new account authenticated | Post-auth identity flush |
| `onboarding_completed` | activated | Preferences/onboarding completed | Onboarding flow |
| `moment_joined` | activated | User joined a real Moment | Participation API |
| `proof_submitted` | outcome | Proof entered review | Proof/participation service |
| `verified_outcome` | outcome | Proof was approved | Proof/participation service |
| `share_created` | amplified | Trackable sharing path created | PromoShare/referral adapters |
| `referral_signup` | captured | Stored referral was claimed | Growth operations API |
| `referral_activated` | amplified | Referred user met activation rules | Referral service |
| `checkout_started` | captured | Commercial checkout began | Revenue funnel mirror |
| `payment_succeeded` | monetized | Provider-verified payment succeeded | Stripe/revenue funnel mirror |
| `repeat_outcome` | retained | Verified outcome occurred at least seven days after an earlier outcome | Database trigger |

Domain tables remain authoritative. `growth_events` is a reporting and learning projection, not a replacement for proof, payment, referral, or reward ledgers.

## Attribution rules

1. Generate a stable anonymous ID in first-party local storage.
2. Store first touch permanently and update last touch only when a new campaign signal exists.
3. Preserve `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, referral code, and PromoPush identifiers.
4. Link the anonymous ID to the authenticated user after login or signup.
5. Backfill the user ID onto earlier anonymous events.
6. Provider webhooks remain authoritative for money events.
7. Proof approval remains authoritative for verified outcomes.
8. Every retryable event must have an idempotency key.

## Scorecard

The Admin Dashboard **Growth** tab reports the last 28 days by default.

Primary metric:

- Verified outcomes per active Moment

Supporting metrics:

- Visitor → signup rate
- Signup → activation rate
- Activation → amplification rate
- Seven-day repeat-outcome rate
- Activated referrals
- Outcomes and signups by attributed source
- Attributable revenue
- Verified Pioneer contributors and receipts, reported separately from the funnel

Guardrails to review outside the aggregate scorecard:

- Proof rejection and reversal rate
- Duplicate-event rate
- Reward cost per verified outcome
- Referral fraud/self-referral attempts
- Refund and payment-failure rate
- Marketing opt-out and complaint rate

## Experiment standard

Every experiment must be registered before treatment code ships.

Required fields:

- A falsifiable hypothesis
- Participant or commercial journey
- Primary conversion event
- Guardrail event
- Control and treatment variants
- Allocation percentage
- Start and end dates
- Final decision

Assignments are deterministic for a user or anonymous ID. Event calls made inside a treatment must include the returned `experimentKey` and `experimentVariant`. Do not change variant weights while an experiment is running.

Weekly operating cadence:

1. Monday: inspect the scorecard and select the largest constrained funnel step.
2. Tuesday: register one focused experiment and its guardrail.
3. Wednesday: ship the smallest valid treatment.
4. Thursday–Friday: verify event quality; do not call a winner prematurely.
5. Following review: complete the experiment with a written ship, iterate, or stop decision.

## Deployment

1. Apply `supabase/migrations/202607140003_growth_operating_system.sql`.
2. Deploy the backend with `/api/growth-ops` mounted.
3. Deploy the web application with `GrowthTracker` enabled.
4. Visit a tagged URL and confirm a `page_view` row contains the expected first-touch fields.
5. Create a test account from `?ref=<valid-code>` and confirm:
   - the anonymous identity is linked;
   - the referral is created once;
   - `signup_completed` and `referral_signup` are idempotent.
6. Join a test Moment and approve proof. Confirm `moment_joined` and one `verified_outcome`.
7. Complete a Stripe test checkout. Confirm the provider-owned revenue event and its growth projection.
8. Open **Admin → Growth** and validate totals against source tables before making decisions.

## Privacy and reliability

- Do not place email, phone, names, raw IP addresses, proof media, or payment details in growth-event properties.
- Public ingestion only accepts acquisition events. Outcomes and money events require authentication or server-side adapters.
- Properties are capped at 10 KB.
- Invalid UUID attribution identifiers are discarded instead of breaking event ingestion.
- The scorecard caps a request at 10,000 events; move aggregation into database views before volume approaches that limit.
- Apply edge/API rate limiting to the anonymous ingestion endpoint in production infrastructure.
